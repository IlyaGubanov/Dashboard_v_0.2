# Видеонаблюдение: установка, пилот и эксплуатация

Реализация рассчитана на Dahua DHI-NVR4216-16P-4KS3 (каналы 1–16), 4–7 объектов и примерно 9–12 камер на объект. Только прямой эфир. Запись продолжает выполнять регистратор. Приложение не меняет настройки оборудования, основной поток, архив, PTZ или звук.

## Устройство

`Dahua — RTSP/TCP — MediaMTX 1.21.3 — nginx auth_request — Caddy HTTPS — браузер HLS`.

MediaMTX закреплён на **1.21.3** в Dockerfile. Контракт проверяется по [конфигурации тега](https://github.com/bluenviron/mediamtx/blob/v1.21.3/mediamtx.yml), [Control API](https://github.com/bluenviron/mediamtx/blob/v1.21.3/api/openapi.yaml) и [HLS HTTP server](https://github.com/bluenviron/mediamtx/blob/v1.21.3/internal/servers/hls/http_server.go). Обновление версии требует повторной проверки CDN-режима, API, redirects, авторизации и прекращения чтения без зрителей.

API хранит оборудование в MySQL, шифрует пароли и синхронизирует отдельные пути `cam-ID`. Плейлисты и сегменты идут через nginx, без передачи видеобайтов обработчиками NestJS. HLS fMP4 с сегментами около 2 секунд: задержка несколько секунд, зависит от I-кадров и браузера. hls.js 1.6.16 загружается отдельным чанком при первом воспроизведении. Safari использует нативный HLS, где он поддерживается; на остальных браузерах нужен MediaSource/H.264.

MediaMTX не перекодирует видео. FFmpeg отсутствует в обычном медиасервисе и не запускается для каждой камеры.

## Первый запуск с одним регистратором

1. Подготовить обычное развёртывание приложения по `03-razvertyvanie.md`. Сервер должен иметь маршрут к локальному IP регистратора. Наличие просмотра в DMSS по SN этого не доказывает.
2. Скопировать `.env.example` в `.env` или дополнить существующий файл. Выполнить:
   ```bash
   bash deploy/video-secrets.sh
   ```
   Скрипт создаст только отсутствующие ключ и токены, сохранив существующие. Не выводит их в терминал.
3. Указать **реальную** сеть регистратора в `VIDEO_ALLOWED_NETWORKS` (CIDR через запятую). Пустой список запрещает новые подключения. Здесь намеренно нет выдуманных рабочих IP.
4. Если используется внутреннее DNS-имя, добавить точное имя или разрешённый суффикс в `VIDEO_ALLOWED_DNS_SUFFIXES`. `VIDEO_ALLOWED_PORTS` по умолчанию `554`; другой порт нужно разрешить явно. Форма рассчитана на IPv4 и внутренние DNS-имена.
5. Проверить, что `VIDEO_CONTROL_SUBNET=172.31.250.0/29` не пересекается с существующими сетями. При конфликте выбрать свободную подсеть и согласованный `VIDEO_CONTROL_API_IP`. Это только внутренняя сеть связи API и MediaMTX.
6. Запустить:
   ```bash
   docker compose up -d --build
   docker compose logs --tail=50 api mediamtx
   ```
   Новая миграция `20261031170000_video` применяется штатным запуском API. Создаются таблицы `video_recorder`, `video_camera`, `video_grant`. Реальное оборудование автоматически не добавляется.
7. Администратор → «Настройки видеонаблюдения» → «Регистраторы» → «Добавить регистратор». Выбрать существующую школу, ввести локальный адрес, RTSP-порт и отдельную учётную запись просмотра.
8. «Проверить подключение» проверяет доступность RTSP-порта. **Это ещё не подтверждение пароля или изображения.**
9. «Камеры» → «Добавить камеру». Ввести реальный номер канала (пропуски разрешены), выбрать дополнительный поток. «Проверить изображение» проверяет поток и формат.
10. Открыть школу → «Камеры» или общую страницу «Видеонаблюдение». Проверить 1–2 камеры, затем 4, телефон и повторное подключение. После пилота добавлять остальные каналы и объекты через интерфейс.

`install.sh` и `update.sh` вызывают подготовку отсутствующих секретов. Перед обновлением старой установки скопируйте новый `deploy/video-secrets.sh` вместе с кодом и выполните его до команд Docker Compose: без CDN-токена конфигурация намеренно не запустится.

## Учётная запись Dahua и формат

Создайте в интерфейсе регистратора отдельного пользователя только с просмотром нужных каналов. Не используйте административную учётную запись для постоянного вещания. Названия пунктов прав зависят от прошивки.

Шаблон:
```text
rtsp://<host>:<port>/cam/realmonitor?channel=<1..16>&subtype=<0|1>
```
`subtype=1` — дополнительный, `0` — основной. Логин и пароль кодируются как отдельные компоненты URI, включая `@ : # / %` и кириллицу. Сохранённый пароль никогда не возвращается в форму; пустое поле при изменении оставляет текущий.

Для пилота специалист вручную настраивает **только дополнительный поток**: обычный H.264, около 15 кадров/с, 512–1024 Кбит/с, интервал I-кадров 30. Поддерживаемые значения зависят от камер. Текущий H.265 D1/25fps/512Кбит/интервал50 может не воспроизводиться в части браузеров. При H.265/неподдерживаемом аудио/необычном профиле диагностируется несовместимость; универсальная совместимость не обещается. При необходимости проверьте обычный H.264 без Smart Codec/H.264+ на дополнительном потоке. Основной поток записи не изменяется приложением.

D1 отображается с сохранением пропорций из метаданных видео; изображение не растягивается принудительно до 16:9.

Для проверки RTSP используйте VLC в сети с доступом к регистратору, передавая логин и пароль в диалоге проигрывателя. Не вставляйте рабочий URL с паролем в тикеты, скриншоты или общие журналы.

## Доступ и защита медиаресурсов

Разрешения видео не наследуются из области ввода производственных данных.

| Роль | Просмотр | Управление |
| --- | --- | --- |
| ADMIN | Все действующие объекты | Все действующие объекты |
| MANAGEMENT | Только явно разрешённые объекты | Только объекты с явным правом управления |
| CURATOR | Явный доступ к объекту + членство в направлении | То же + явное управление |
| EDITOR | Явный доступ к объекту + членство в направлении | Запрещено |
| VIEWER | Явный доступ к объекту + членство в направлении | Запрещено |

В карточке сотрудника → «Камеры» выдаются положительные разрешения по объектам. На вкладке «Разделы и возможности» можно дополнительно отключить просмотр/управление видео. Эти ограничения только сужают доступ. Пустой список положительных разрешений запрещает видео, даже если галочки возможностей включены. У администратора ограничения не применяются — это согласуется с существующей ролью администратора. При миграции ни один существующий неадминистративный пользователь не получает разрешений: таблица grant изначально пуста. MANAGEMENT также требует явного назначения.

Каждый запрос к `/media/cam-ID/*.m3u8`, инициализации и сегментам проверяется nginx через существующую cookie-сессию и AccessService. Повторно проверяются действительность сессии, активность сотрудника, обязательная смена пароля, свежие разрешения, объект и доступность оборудования. Кэш авторизации отсутствует. Без сессии скопированная ссылка не работает; право на одну школу не открывает другую.

После выхода/отзыва сессии/блокировки/изменения прав **следующий запрос** к медиа запрещается. Уже скачанные кадры могут доиграть из браузерного буфера: вернуть их с устройства сервер не может. Срок входа — существующий `SESSION_TTL_HOURS`; отдельного публичного бессрочного токена просмотра нет.

Внутренний CDN-токен заменяет пользовательский Authorization только после успешного auth_request. Он не передаётся браузеру. Публичный доступ к внутренним auth endpoints, Control API, HTML-плееру MediaMTX и диагностическим портам закрыт. MediaMTX не публикует Docker-порты и отключает серверы RTSP/RTMP/WebRTC/SRT/MoQ, запись и playback. Публичен только существующий HTTPS-вход Caddy. Все HLS-ответы получают `Cache-Control: private, no-store`.

CSP расширена только `media-src 'self' blob:`; workers плеера отключены, поэтому не требуется разрешать сторонние scripts/workers. Запрет доступа к микрофону и локальной камере браузера сохраняется.

## Сети и защита проверок

Назначения прав на архивные объекты не дают просмотра. При редактировании сотрудника интерфейс предупреждает, сколько таких назначений будет снято при сохранении, и позволяет сохранить права остальных действующих объектов.

API разрешает только шаблон RTSP Dahua, валидирует адрес, порт и канал. DNS-имя должно принадлежать разрешённому суффиксу, все полученные IP должны входить в разрешённые сети; в MediaMTX передаётся числовой адрес. Loopback, link-local/metadata и multicast запрещены.

RTSP может перенаправить клиента на другой адрес, поэтому одного закрепления DNS недостаточно. Контейнер MediaMTX дополнительно ограничивает исходящий трафик через iptables: сети/порты регистраторов, Docker DNS и стабильный адрес API на внутренней сети. После настройки firewall MediaMTX запускается непривилегированным UID 10001. Для начальной настройки namespace нужны NET_ADMIN/SETUID/SETGID; основная файловая система read-only. На хосте должен работать iptables/ip6tables в сетевом namespace контейнера. Самостоятельно снимать эти ограничения при ошибке запуска не следует: сначала проверить журнал и поддержку firewall.

Проверки подключения имеют таймаут 3 секунды; проверка изображения — до 15 секунд плюс синхронизация. Одна камера/регистратор проверяется не чаще раза в 30 секунд; API дополнительно ограничивает пользовательские запросы диагностики. Обычные медиазапросы и внутренние callbacks исключены из общего лимита 600 запросов/мин, чтобы сетка камер и пользователи за одним NAT не блокировали друг друга.

При развёртывании проверить маршрут **из namespace MediaMTX**, а не только с офисного компьютера. Docker bridge должен иметь доступ к школьным сетям; ACL/VPN/маршруты и обратный путь настраиваются администратором сети. В этой задаче сетевое оборудование не изменяется.

## Нагрузка и синхронизация

`sourceOnDemand=true`, `hlsAlwaysRemux=false`. Один входящий поток камеры разделяется между зрителями; браузеры получают собственные исходящие потоки. После последнего запроса muxer закрывается примерно через 10 секунд, затем RTSP-source через 5 секунд (с учётом периодических проверок возможен небольшой запас). Отсутствие зрителей не является ошибкой камеры. Реконсиляция не запрашивает HLS и не держит источники запущенными.

По умолчанию интерфейс выбирает страницу максимум из 4 камер, доступны раскладки 1/4/9. На телефоне один активный поток. Невидимые плитки и скрытая вкладка браузера приостанавливаются. При закрытии карточки, смене страницы/камеры и размонтировании уничтожаются HLS, события и таймеры. Повторные попытки ограничены; затем доступна кнопка «Повторить».

При 4 камерах по 512 Кбит/с один зритель получает около 2 Мбит/с видеоданных плюс накладные расходы. Вычислительных ресурсов по условию достаточно; исходящий канал сервера растёт с числом зрителей, входящий — с числом различных просматриваемых камер, а не со всем каталогом 36–84 камер.

БД — источник истины. Изменения запускают сверку, дополнительно она идёт каждые 20 секунд. После перезапуска MediaMTX отсутствующие пути восстанавливаются. Обновляется только изменённый путь. API MediaMTX 1.21.3 возвращает скрытые credentials: сравнение выполняется по локальному SHA-256 применённого подключения и наличию пути, а не по redacted URL. После перезапуска API выполняется первичная сверка всех путей. Рекомендуется один экземпляр API-реконсилятора.

До подтверждения применения изменённая камера имеет PENDING и не выдаёт видео. Ошибка показывает ERROR; синхронизация повторяется. Сохранение формы означает сохранение БД, а не ложное подтверждение доступности MediaMTX. Для SOURCE/ERROR нет автоподмены на «В эфире».

## Отключение, архив и одновременное редактирование

Временное отключение сохраняет запись и резервирует канал. Любая неархивная камера занимает свой канал на регистраторе независимо от enabled; БД обеспечивает уникальность.

Архивирование камеры освобождает канал. При восстановлении занятого канала возвращается конфликт, запись остаётся архивной. Сначала освободите канал другой записью либо восстановите после изменения состава оборудования. Архивирование регистратора показывает список затрагиваемых камер и приостанавливает их, сохраняя связи и индивидуальные состояния. Восстановление не включает ранее отключённые или отдельно архивированные камеры.

Изменения используют version; устаревшая форма не перезаписывает свежие данные. Перенос регистратора между объектами требует права управления обоими объектами. Изменения и выдача доступа пишутся в штатный журнал без паролей, токенов и RTSP URL с credentials.

## Ключи, копирование и восстановление

`VIDEO_ENCRYPTION_KEY` — 32 случайных байта base64 для AES-256-GCM. БД содержит только версионированный ciphertext, nonce и authentication tag. Ключ находится в приватном `.env`, вне БД и git. `VIDEO_SERVICE_TOKEN` и `VIDEO_CDN_TOKEN` — разные случайные внутренние токены.

`backup.sh` сохраняет приватный `secrets-ДАТА.env` с правами 600 рядом с дампом БД; каталог имеет права 700. Сохраняйте его вместе с соответствующим дампом на защищённом носителе. Потеря ключа делает сохранённые пароли невосстановимыми: потребуется восстановить ключ или заново ввести пароли регистраторов.

Перед восстановлением БД восстановите **тот же** VIDEO_ENCRYPTION_KEY из secrets-файла соответствующей копии, не выводя файл целиком в общие журналы. Сохраните остальные настройки текущего сервера. Восстановление останавливает web/MediaMTX/API; после изменения .env контейнер API нужно пересоздать, а не только стартовать:
```bash
docker compose up -d --no-build api mediamtx web
```
Неподходящий ключ даёт безопасную ошибку синхронизации, не открытый пароль.

Не заменяйте ключ случайным значением при обычном обновлении. Плановая ротация требует окна обслуживания: расшифровать все recorder-пароли старым ключом, зашифровать новым в одной контролируемой операции, сохранить новую согласованную копию БД+ключа и пересоздать API. Автоматической ротации в этой версии нет. Внутренние токены можно заменить согласованно в .env и пересоздать API/web/MediaMTX.

## Диагностика

| Симптом | Что проверить |
| --- | --- |
| Регистратор: «Нет связи» | Маршрут из Docker, адрес, порт, ACL/VPN, VIDEO_ALLOWED_NETWORKS/PORTS |
| Порт доступен, изображения нет | Права отдельного пользователя на выбранный канал, пароль, реальный номер канала |
| Несовместимый формат | Обычный H.264 дополнительного потока, параметры профиля; H.265 не гарантируется |
| Синхронизация «Ошибка» | MediaMTX, ключ, allowlist, стабильная control-сеть, внутренние токены |
| Нет доступа | Живая сессия, разрешение объекта, членство направления, ограничения возможностей |
| Камера отключена | enabled/archive камеры и регистратора, архив объекта |
| После ухода зрителя source ещё активен | Подождать idle grace; убедиться, что другая вкладка/зритель/проверка не читает HLS |

Диагностика регистратора различает «порт доступен» и подтверждённое изображение. Состояние «В эфире» устанавливается только событием playing браузерного видео. Ошибки не включают секреты и полный RTSP-адрес.

## Воспроизводимый тестовый источник

Обычное развёртывание его не запускает. Для отдельного тестового стенда:
```bash
docker compose -f docker-compose.yml -f docker-compose.video-test.yml --profile video-test up -d --build
```
Источник `video-test-source:8554` выдаёт H.264 704×576/15fps/512Кбит, без звука, как цветной движущийся тестовый рисунок. Разрешите только его тестовую Docker-сеть, имя `video-test-source` и порт 8554 в тестовом .env, затем добавьте запись с названием **«ТЕСТ · генератор H.264»**. В протоколе тестового источника channel/subtype не выбирают реальные камеры; один рисунок предназначен для проверки доставки/плеера. Не оформляйте его как рабочую школьную камеру.

`scripts/video-qa-fixture.ts` дополнительно создаёт фиксированный набор **только** в изолированной базе `video_test`: 3 тестовых регистратора, 15 камер, из них 14 неархивных; первая школа — 11 видимых, одна камера отключена, один регистратор отключён. Требуются предварительные seed и demo школ, реальный адрес локального тестового источника в VIDEO_QA_SOURCE_HOST и тестовый ключ. Скрипт отказывается работать с другим именем БД.

## Проверки перед пилотом

Для Vite-разработки интерфейса существующая команда запуска сохраняется. Сквозную проверку видео выполняйте через nginx/Caddy (Docker или отдельный тестовый прокси), поскольку обычный Vite proxy обслуживает только API и не заменяет защищённый медиашлюз.

```bash
npm run typecheck
npm run build
npm test -w @mvs/api
# Дополнительно: только отдельная БД с применёнными миграциями
VIDEO_TEST_DATABASE_URL=mysql://.../video_unit npm test -w @mvs/api -- src/video
```

Итоги выполненных проверок, screenshots и остающиеся проверки реального Dahua приведены в [video/verification.md](video/verification.md). Подключение физического Dahua, достижимость его адреса из контейнера, Linux firewall и целевые Safari/телефоны проверяются на пилотном стенде; результаты синтетического H.264 не подменяют эти проверки.
