## Ключевые правила

1. **История не затирается.** Факт хранится строкой на (позиция, период) — `progress_entry`. Срез «на любую неделю» — это выборка по периоду.
2. **Кто внёс.** В `progress_entry`/`site_report` — `entered_by_id`, `entered_at`, `updated_by_id`, `source` (вручную / импорт / перенос). Полная история значений — в `audit_log` (было → стало).
3. **Кто куратор.** `direction_member.role = CURATOR` — куратор направления; `site_assignment.role = CURATOR / ENTRY` — куратор и ответственный за ввод конкретного объекта.
4. **Демо-данные** помечены `is_example = 1` — их можно показать пунктиром и удалить одним запросом, когда появятся реальные.
5. **Защита от одновременной правки** — колонка `version` у `site` и `progress_entry`.
6. **Закрытые периоды.** `reporting_period.status`: OPEN → CLOSED (правит только куратор) → LOCKED (только администратор).
   В сводке видны и незакрытые недели — с пометкой «не проверено куратором».

## Решения, утверждённые заказчиком (28.10.2026)

| Вопрос | Решение | Где в БД |
|---|---|---|
| Кто назначает ответственных | администратор вносит людей и назначает их по направлениям | `user`, `direction_member` |
| Права ответственного за ввод | всё направление / выбранные лоты и разделы / только назначенные объекты | `direction_member.scope`, `direction_member_section`, `site_assignment` |
| Сводка до проверки куратором | видно всё, непроверенное помечено | `reporting_period.status` |
| Пороги светофора | как в дашборде: объекты −5/−15 п.п. (МКД, Сети), направление в сводке −2/−10 п.п. | `direction.thr_*`, `app_setting['overview.thresholds']` |
| День плана в отчётной неделе | **среда** для всех недельных направлений | `direction.plan_weekday = 3` |
| Подрядчики | свой справочник в каждом направлении | `organization.direction_id` |
| Удаление | архив вместе с историей, насовсем — только администратор | `is_archived` |
| Пароли | от 10 символов, буквы и цифры; сессия 12 ч; после 5 неудачных попыток — блокировка на 15 минут или до разблокировки администратором | `user.failed_logins`, `user.locked_until` |

Из-за перехода на среду плановая готовность МКД и Сетей будет немного отличаться от исходного дашборда (там были пятница и понедельник).

## Как добавить новое направление (без изменения кода)

1. `direction` — название, `period_kind`, `progress_method`, `plan_method`, `money_source`, пороги.
2. `section` — разделы/лоты; `work_group` + `work_type` — виды работ (с весами, если формула по весам).
3. `status_def` — свои статусы позиций или объектов.
4. `field_def` — свои поля объекта/позиции (значения лягут в `attrs`).
5. `tracker` + `tracker_item` + `tracker_stage` — свои надстройки (например, «Согласования» с этапами).
6. `direction_member` — куратор и ответственные.

На этапе 8 всё это будет делаться из админки.

## Как исходные данные дашборда ложатся в таблицы

| Было (HTML-модуль) | Стало |
|---|---|
| МКД: `objects`, `items`, `snaps[item][week]` | `site`, `work_item`, `progress_entry` (+ `reporting_period` на каждую неделю) |
| МКД: `people`, `orgs`, `curatorId`, `entryId` | `user` (без входа), `organization`, `site_assignment` |
| Сети: `objects[].contracts`, `lines` | `contract`, `work_item` (линия прокладки = позиция) |
| Сети: `weekly[week][obj] = {f, ks, w, m}` | `progress_entry.fact_qty` по линиям, `site_report` (КС, рабочие, техника) |
| Сети: `docs` (ПСД, РД, МГЭ, согласования, ордер) | трекер «Документация» |
| Школы: `works{pct, pv, fv}`, веса видов работ | `work_item` + `progress_entry`, `work_type.weight` |
| Школы: `proc`, `ii`, `mge` | трекеры «Закупки», «Индивидуальные испытания», «МГЭ» |
| Школы: `res`, `log/{дата}_{объект}` | `site_report` на дневные периоды |
| Школы: площадь, тип, пищеблок, лимиты | `field_def` + `site.attrs`, `site.limit_amount` |
| Благоустройство: `snapshots[{date, program, objects}]` | `reporting_period` (с `program`), `work_item`, `progress_entry`, `site_report` (люди, техника, статус, число замечаний) |
| Благоустройство: геокодинг | `site.lat`, `site.lon` |

| Благоустройство | 37 (КБУ + текущий ремонт) | 607 | 140 отчётов | 38 080 | 4 112 | координаты 34 улиц, сведения о расхождениях в исходном Excel |

**Сверка:** `npm run db:demo:verify` пересчитывает из БД 31 показатель «Сводки» (готовность, план, отстающие, критичные,
люди, техника, деньги) по формулам исходных модулей — все совпадают. Сверка идёт по исходным правилам дня плана
(МКД — пятница, Сети — понедельник, Школы — 27.10.2026); в приложении план будет считаться на среду.

**Что выяснилось при переносе:**
- Сети: сумма договоров отличается на 1,5 копейки — в исходнике были доли копеек, в БД суммы хранятся с точностью до копейки.
- Сети: у 2 объектов названия длиннее 500 символов (до 583) — поле `site.name` расширено до 1000.
- Сети: «Готовы к конкурсу (2 этапа)» в поле подрядчика — это состояние, а не организация; перенесено в доп. поле «Подрядчик (примечание)».
- Школы: выполнение видов работ в исходнике — один срез на 23.10.2026, без истории. Динамика готовности школ начнёт копиться с первого ввода в приложении (динамика людей и техники есть за 45 дней).
- У Школ, Сетей и Благоустройства в исходных данных нет куратора направления — его нужно назначить в «Пользователи и роли».
- Благоустройство: все отчёты помечены как заблокированные (LOCKED) — это загруженные отчёты, их не правят вручную.
- Сотрудники из данных заведены пользователями без входа (14 человек); дать вход — «Дать доступ» в админке.
