# Как ИИ работает с этим репозиторием

Эти инструкции действуют во всех каталогах для Codex, Claude, Copilot и других ИИ.
Команда небольшая и доверяет участникам: это рабочие договорённости для ИИ, а не ограничения прав людей.
Обязательные approvals владельца, CODEOWNERS, branch protection и проверки направления PR не требуются.
Человек может коммитить в выбранные им ветки. ИИ по умолчанию следует сценарию ниже;
явное поручение пользователя на конкретную ветку или действие имеет приоритет.

## Перед началом

1. Прочитать этот файл и `CLAUDE.md` (стек, команды, особенности проекта).
2. Проверить `git rev-parse --show-toplevel`, `git remote -v`, `git branch --show-current`,
   `git status --short --branch`, `git worktree list --porcelain`; затем `git fetch origin`.
3. Не трогать чужие незакоммиченные изменения, ветки и worktrees. Не выполнять автоматически reset,
   clean или stash. Если каталог занят другой сессией, создать свой worktree.

## Обычная новая задача

- `main` — стабильная версия/production; `dev` — общая интеграция и будущая тестовая среда.
- Создать свою свободную `mvsst-N` от свежей `origin/dev`. Один исполнитель — одна активная ветка.
  Проверить локальные и удалённые ветки и PR; не занимать уже используемый номер. Для новой независимой
  задачи брать новый номер. Не создавать ветки впрок. Примеры — `docs/GIT_WORKFLOW.md`.
- Реализовать только поставленную задачу, выполнить проверки, закоммитить и отправить свою ветку.
- По умолчанию открыть PR в `dev` и сообщить результат. Если пользователь поручил объединить изменения
  в dev, выполнить merge после проверок; отдельное обязательное согласование владельца не нужно.
- При продолжении существующей задачи использовать указанную пользователем ветку, предварительно
  проверив её состояние и отсутствие другого активного исполнителя. Не начинать её заново без причины.
- Отставшую опубликованную ветку обновлять через `git merge origin/dev`; сохранять обе стороны конфликта.
  Не переписывать опубликованную историю автоматически.

## Main и развёртывание

- Обычную разработку не вести прямо в main или dev, если пользователь явно не поручил другое.
- Выпуск в main по умолчанию идёт из dev. Создание/merge такого PR выполнять по прямому поручению
  пользователя, без дополнительных требований к его GitHub-роли или формальному approve.
- Поручение перенести инструкции в main разрешает только организационные изменения, а не новый функциональный выпуск.
- Поручение изменить main не означает разрешения подключаться к серверу или запускать deploy.
  Деплой — отдельное явное задание. Автодеплой dev будет настраиваться отдельно.
- После выпуска вернуть историю main в dev через новую рабочую ветку и PR; без force push/reset dev.

## Проверка и завершение

- Перед сдачей: `npm ci`, `npm run db:generate`, `npm run build -w @mvs/shared`, `npm run typecheck`,
  `npx tsc --noEmit -p apps/api/prisma/tsconfig.json`, `npm run test -w @mvs/api`, `npm run build`.
  Тесты с БД запускать на отдельной тестовой БД; существующий CI использует одноразовый MySQL.
  Для правок только документации проверить ссылки и согласованность; для workflows — также синтаксис и их запуск.
- Сообщить ветку, коммит/PR, выполненные проверки и пропуски, объединены ли изменения в dev/main.
  Не выдавать открытый PR за выполненный merge и не обещать автоматическое соблюдение инструкций любой моделью.
- Не удалять чужие/удалённые ветки и worktrees без поручения; не делать force push main/dev или push --mirror.
- Не добавлять секреты, личные пути, временные логи и настройки. Не менять доступы GitHub или включать
  дополнительные ограничения без отдельного задания.
