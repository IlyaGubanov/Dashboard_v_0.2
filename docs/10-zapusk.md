# 10. План запуска

Пять шагов от пустого сервера до работы 200 человек. Ориентир по времени — 3–4 недели, из них 1–2 недели пилот.

## 0. Что подготовить заранее

| Что | Кто | Зачем |
|---|---|---|
| ВМ в Hyper-V: Ubuntu Server 24.04, 4 vCPU, 8 ГБ ОЗУ, диск 60 ГБ | ИТ | сервер приложения ([03-razvertyvanie.md](03-razvertyvanie.md), п. 1) |
| Домен (например, `dashboard.mvs-st.ru`), DNS-запись A на внешний IP | ИТ | адрес для пользователей |
| Проброс портов 80 и 443 на ВМ | ИТ | доступ извне и бесплатный сертификат |
| Решение по сертификату: `auto` / свой корпоративный (`files`) | ИТ, безопасность | HTTPS |
| Место для копий **вне** ВМ (сетевой диск, другой сервер) | ИТ | восстановление при потере ВМ |
| Список кураторов по направлениям | руководство | кто проверяет и закрывает недели |
| Список пользователей в шаблоне (ФИО, должность, направление, роль, лоты) | кураторы | загрузка списком |

## 1. Установка (день 1)

1. Скопировать код на ВМ и запустить `sudo bash deploy/install.sh`. Для первой установки демо-данные можно оставить: на них удобно показывать.
2. Войти администратором, сменить пароль.
3. Проверить снаружи (с телефона по мобильному интернету):
   - [ ] `https://<домен>` открывается, в адресной строке замок;
   - [ ] `http://<домен>` перенаправляет на https;
   - [ ] `https://<домен>/api/docs` — 404 (документация API снаружи закрыта);
   - [ ] вход, сводка, направление, фото к замечанию загружается.
4. **Проверить копии:** `sudo bash deploy/backup.sh` — в `/var/backups/mvs` должны появиться `db-….sql.gz` и `files-….tar.gz`,
   в выводе — «таблиц 3x». Восстановление стоит один раз проверить на отдельной тестовой ВМ: развернуть там приложение
   и выполнить `bash deploy/restore.sh` с этими файлами.
5. Настроить вынос копий с ВМ (например, ежедневный `rsync` каталога `/var/backups/mvs` на сетевой диск).

## 2. Пилот на демо-данных (1–2 недели)

Одно направление (например, МКД), куратор и 2–3 ответственных за ввод:

1. Администратор заводит их через «Пользователи и роли» → «Загрузить списком», раздаёт логины и временные пароли лично.
2. Неделя проходит полностью: куратор открывает неделю → ответственные вносят факт (в том числе с телефона) →
   выставляются и закрываются замечания с фото → куратор закрывает неделю → руководство смотрит сводку.
3. Собрать замечания пользователей: что неудобно, чего не хватает, где названия непонятны.

## 3. Переход на реальные данные

По каждому направлению, когда куратор готов:

1. Сделать копию: `sudo bash deploy/backup.sh`.
2. Удалить демо-данные направления (объекты, факт, демо-сотрудники; настройки, статусы и учётные записи остаются):
   ```bash
   docker compose exec api npx tsx prisma/demo/import.ts --clear --only=mkd
   ```
   Коды направлений: `schools`, `mkd`, `networks`, `streets`. Без `--only` — все сразу.
   После очистки демо-данные в это направление **не вернутся** при перезапуске, даже если `DEMO_DATA=true`.
   Когда очищены все направления, поставьте в `.env` `DEMO_DATA=false`.
3. Куратор заводит реальные объекты и позиции на вкладке «Управление» (разделы и лоты, виды работ, подрядчики, объекты, позиции).
4. Администратор загружает пользователей направления списком и назначает ответственных на объекты.
5. Куратор открывает первую неделю — ответственные вносят факт.

Новое направление (не из исходных четырёх) — «Конструктор направлений» → «Новое направление» по образцу похожего.

## 4. Обучение

- В приложении есть **«Справка»** (внизу меню): короткие шаги по ролям, раздел пользователя открыт первым.
- Показ по 30 минут для каждой группы:

  | Группа | Что показать |
  |---|---|
  | Ответственные за ввод | вход и смена пароля → «Мои задачи» → ввод факта с компьютера и телефона → «Без изменений» → замечание: «взять в работу», «устранено» + фото |
  | Кураторы | цикл недели (открыть → контроль на «Ответственные» → закрыть) → «Управление»: объект и позиции → замечания: выставить, принять, вернуть → журнал |
  | Руководство | сводка: цвет направлений, прогноз, «не проверено» → направление → объект → выгрузка в Excel |

## 5. Эксплуатация

| Когда | Что | Кто |
|---|---|---|
| ежедневно, автоматически | резервная копия в 02:30 | сервер |
| еженедельно | вынос копии с ВМ, проверка `docker compose ps` и места на диске | ИТ |
| ежемесячно | контрольное восстановление копии на тестовой ВМ | ИТ |
| по мере выхода | обновление `sudo bash deploy/update.sh` (сначала делает копию) | ИТ |
| при увольнении | «Пользователи и роли» → «Заблокировать» | администратор |
| по необходимости | новые направления, статусы, поля, показатели — «Конструктор направлений» | администратор |

Сертификат в режиме `auto` продлевается сам. В режиме `files` — заменить файлы в `deploy/certs/` до истечения срока
и выполнить `docker compose restart caddy`.

## Что проверено перед запуском

- **Чистая установка** на пустой базе — та же последовательность, что выполняет контейнер при первом старте (миграции →
  справочники → демо-данные): 20 секунд; все показатели сводки совпали с исходным дашбордом; 16 модульных тестов
  (в том числе 8 сверок расчёта с дашбордом) — без ошибок.
- **Защита от повторной загрузки демо:** после очистки направления перезапуск не возвращает демо-данные.
- **Загрузка пользователей списком** — 18 сквозных проверок (распознавание ролей, направлений, лотов; понятные ошибки;
  проверка без изменений; временные пароли; повторная загрузка того же файла не создаёт дублей; ФИО существующих не меняются).
- **Скрипты** `install.sh` (создание `.env`, генерация паролей), `backup.sh`, `restore.sh`, `update.sh` — синтаксис; создание `.env`
  проверено запуском.

## Что проверить на сервере (здесь не было Docker)

- Первый запуск `docker compose up` и выпуск сертификата Caddy (Caddyfile не проверен запуском).
- `backup.sh` / `restore.sh` — первый ручной запуск по п. 1.4.

## Чего нет и можно добавить по итогам пилота

- Напоминания на почту — нужен SMTP-сервер организации.
- Загрузка объектов и позиций списком из Excel — если заводить вручную на вкладке «Управление» окажется долго.
- Работа без связи (ввод на объекте без интернета с отправкой позже).
