# Как работаем с Git

Основные инструкции ИИ — [AGENTS.md](../AGENTS.md), технические сведения — [CLAUDE.md](../CLAUDE.md).
Для запуска нового чата достаточно [короткого промпта](AI_PROMPTS.md).

## Общая договорённость

| Ветка | Для чего |
|---|---|
| main | Стабильная версия, источник production |
| dev | Совместная интеграция, источник будущего тестового развёртывания |
| mvsst-N | Отдельная задача одного ИИ/разработчика |

Обычный сценарий ИИ: **origin/dev → mvsst-N → PR в dev → по поручению dev → main**.
Люди сохраняют возможность коммитить в выбранные ими ветки. Формальный approve владельца,
административные блокировки и обязательный контроль названия исходной ветки не вводятся.
Review полезен, но не является обязательным ритуалом. CI помогает увидеть ошибки и не требует
назначать владельца единственным согласующим. Default branch можно оставить main: ИИ явно выбирает dev.

## Новая задача

1. Прочитать AGENTS.md и CLAUDE.md, проверить status, ветку и worktrees; выполнить `git fetch origin`.
2. Посмотреть локальные/удалённые mvsst-N и историю PR, выбрать следующий свободный номер.
   Если номер уже занят, взять другой; не продолжать чужую работу без указания пользователя.
3. Создать ветку от актуальной origin/dev. При параллельных сеансах создать отдельный worktree.
4. Выполнить задачу и проверки, отправить коммиты и открыть PR в dev.
5. Если поручено «внедрить в dev» — объединить после проверок; иначе сообщить ссылку на готовый PR.

Для одного исполнителя в чистом свободном каталоге:

```bash
git switch -c mvsst-N origin/dev
```

Для параллельной работы:

```bash
git worktree add -b mvsst-N ../mvsst-N origin/dev
```

N заменить свободным номером. При одновременном старте двух исполнителей лучше заранее назначить
им разные номера. При автоматическом резервировании использовать создание новой ветки в GitHub/API,
которое завершается ошибкой при существующем ref. Обычный push одинакового SHA не подтверждает,
что номер зарезервирован только одним исполнителем. Не создавать пустые ветки про запас.

## Продолжение и обновление

Для незавершённой задачи использовать её ветку, если пользователь указал её и другой исполнитель
в ней сейчас не работает. Проверить изменения и PR, а не создавать дубликат задачи.
Перед обновлением своей ветки проверить чистоту каталога, затем `git fetch origin` и `git merge origin/dev`.
Конфликты разбирать по обеим сторонам и истории. Не применять массовое ours/theirs и принудительный
rebase опубликованной ветки. Если решение непонятно — отменить merge и уточнить конкретный конфликт.

## Проверки

Команды перечислены в AGENTS.md и CLAUDE.md. Для документации достаточно проверки текста, ссылок
и отсутствия противоречий; изменение workflows также проверяется actionlint и реальным CI.
При изменении приложения запускать типы, тесты и сборку. DB-тесты — только на тестовых данных.
GitHub CI создаёт отдельные одноразовые MySQL-базы; пропуски локальных тестов сообщать честно.
Ошибки CI разбирать по существу: не скрывать их, но и не менять посторонний код без поручения.

## Перенос dev в main

Пользователь пишет «перенеси проверенную dev в main». ИИ проверяет состав изменений и тесты,
открывает PR dev → main и объединяет его merge-коммитом. Отдельного approve владельца или
административного подтверждения не требуется. Если появились посторонние/непроверенные изменения,
перед слиянием сообщить о конкретной проблеме. Сервер при этом самостоятельно не обновлять.

После выпуска создать новую mvsst-N от свежей dev, выполнить `git merge origin/main` и объединить
её через PR в dev. Это возвращает merge-коммит релиза в общую историю без переписывания веток.
Сценарий проверяется `.github/scripts/sync-strategy.test.cjs`. Если люди отдельно обновили main,
тем же способом синхронизировать её историю и изменения в dev, сохранив обе стороны.

## Завершённые ветки и серверы

Сообщить итог, ссылку на PR, результаты проверок и состояние main/dev. Завершённые ветки можно
оставить; удаление старых веток и чужих worktrees выполняется только по отдельному поручению.
Не трогать ветку с уникальными неинтегрированными коммитами только потому, что её PR закрыт.
Будущий автодеплой dev на тестовую VM и production-деплой — отдельные задания. Push mvsst-N
ничего не развёртывает; существующий CI проверяет код и не подключается к серверу.
