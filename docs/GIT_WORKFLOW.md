# Разработка и выпуск МВС СТ

Обязательные правила для всех исполнителей находятся в [AGENTS.md](../AGENTS.md).
Здесь — практическое руководство. Состояние внедрения: [аудит](GIT_AUDIT_2026-11-01.md),
включение технической защиты владельцем: [GITHUB_PROTECTION.md](GITHUB_PROTECTION.md).

## Назначение веток

| Ветка | Назначение | Допустимый вход |
|---|---|---|
| main | Стабильный production | Только dev → main, приёмка и явный approve владельца |
| dev | Постоянная интеграция; источник будущего тестового развёртывания | Только mvsst-N → dev, CI и review |
| mvsst-N | Одна задача, один исполнитель/сеанс | Создаётся от актуальной origin/dev |

Production всегда использует явно выбранную main, независимо от default branch GitHub.
В будущем merge в dev запускает CI и затем обновление тестовой VM; push mvsst-N ничего не развёртывает.
Сейчас workflows выполняют только проверки: подключение VM и автодеплой будут отдельной задачей.

## Начало задачи и резервирование номера

Проверить репозиторий, текущую ветку, status и все worktrees командами из AGENTS.md.
При незакоммиченных чужих изменениях оставить дерево владельцу и создать отдельное.
Получить актуальные refs: `git fetch origin`; посмотреть `git branch -a` и `git worktree list --porcelain`.
Проверить все PR, включая закрытые, и назначения исполнителей. Выбрать N больше максимального ранее
использованного номера среди локальных/удалённых веток и истории PR. Удалённые номера не переиспользовать.
Не занимать существующий номер только потому, что ветка давно не обновлялась.

Резервировать номер нужно атомарным созданием ref на GitHub: операция POST /git/refs
возвращает ошибку, если ref уже существует. Пример с GitHub CLI (N заменить выбранным номером,
SHA_DEV — полным SHA актуальной origin/dev, путь worktree — своим свободным каталогом):

```bash
gh api --method POST repos/IlyaGubanov/Dashboard_v_0.2/git/refs -f ref=refs/heads/mvsst-N -f sha=SHA_DEV
git fetch origin
git worktree add -b mvsst-N ../mvsst-N origin/mvsst-N
git -C ../mvsst-N branch --set-upstream-to=origin/mvsst-N mvsst-N
```

При ошибке «reference already exists» взять следующий номер, не обновлять чужой ref.
Без gh использовать штатное создание новой ветки в GitHub или API через доступный инструмент,
с обязательной ошибкой при уже существующем ref. Обычный push не резервирует номер: два исполнителя
с одинаковым SHA могут оба получить успех. Резервирование выполнять только для конкретной задачи,
сообщить назначение владельцу.
В описании PR указать задачу, исполнителя/сеанс и исходный SHA dev. Не хранить личные пути в Git.

## Разработка, обновление и проверки

В своём дереве делать изменения и коммиты. Для обновления опубликованной ветки:

```bash
git status --short --branch
git fetch origin
git merge origin/dev
```

Конфликты изучать по обеим сторонам и истории, не применять массовое «ours/theirs».
Если результат непонятен — `git merge --abort` и согласование с ответственным. Не терять чужие изменения.
После разрешения конфликтов повторить проверки. Не делать принудительный rebase опубликованной ветки.

Обязательный минимум (Node.js 22+):

```bash
npm ci
npm run db:generate
npm run build -w @mvs/shared
npm run typecheck
npx tsc --noEmit -p apps/api/prisma/tsconfig.json
node --test .github/scripts/pr-policy.test.cjs .github/scripts/sync-strategy.test.cjs
npm run test -w @mvs/api
npm run build
```

`npm run typecheck` использует существующие workspace-скрипты; дополнительный tsc проверяет Prisma-утилиты.
GitHub CI поднимает одноразовый MySQL 8 с отдельными БД для демо/KPI, карты, отчётов, РЭБ, панорам и видео.
Все схемы мигрируются и наполняются штатным seed; демо импортируется в KPI-БД.
Локально отсутствие DATABASE_URL и *_TEST_DATABASE_URL пропускает DB-наборы: это нужно сообщить,
полноценный CI всё равно обязателен. Не брать URL production или существующих рабочих БД.
Браузерные/сквозные проверки добавлять по затронутому поведению; CI этого задания их не заменяет.

## PR и review

Опубликовать свою ветку, открыть PR **в dev**, проверить base/head перед отправкой.
Не отправлять PR напрямую из старых веток: необходимые изменения переносить в новую mvsst-N от dev
после отдельного решения об их актуальности. GitHub gate проверяет и имя, и ID/полное имя исходного репозитория.
Fork с названием dev или mvsst-N не является разрешённым источником.

Ревьюер проверяет объём, тесты, конфликты, миграции и права; изменения контроля Git требуют отдельного поручения.
CODEOWNERS назначает владельца на все файлы; при включённой защите требуется его approve, включая dev.
Автор PR не может approve собственный PR: release PR по прямому поручению открывает другой участник,
а владелец выполняет приёмку и review. Новые изменения сбрасывают устаревшее согласование.
После зелёных `PR direction` и `Quality`, approve и разрешения обсуждений — **Create a merge commit**.
Сообщить ссылку, SHA, результаты тестов и факт merge; не называть открытый PR интегрированным.

## Выпуск dev → main

Только по отдельному прямому поручению владельца на конкретный выпуск:

1. Зафиксировать проверенный SHA dev и результаты приёмки тестовой версии.
2. Проверить, что текущая main — предок dev. Если нет, сначала синхронизировать по процедуре ниже.
3. Открыть PR dev → main в том же репозитории; не добавлять рабочие изменения во время приёмки.
4. Дождаться обоих обязательных checks и явного человеческого approve @IlyaGubanov именно этой версии.
5. Выполнить merge-коммит. Squash/rebase выпуска не применять: они теряют связь истории постоянных веток.
6. Production-развёртывание выполняется по отдельной политике и поручению; успешный PR не разрешает
   агенту запускать deploy/update.sh, SSH или серверные операции.

Служебные изменения идут тем же путём. Метки, названия PR или аккаунт агента не дают исключений.
Срочное исправление production: новая mvsst-N от dev, минимальный fix, CI/review → dev,
ускоренная приёмка владельцем → разрешённый выпуск dev → main. Если dev содержит неготовый код,
владелец выбирает его revert через отдельный PR; нельзя незаметно выпускать его вместе с hotfix.
Рабочую ветку от main и прямой hotfix → main не использовать.

## Синхронизация без переписывания истории

GitHub создаёт дополнительный merge-коммит при dev → main; сразу после выпуска main может быть
впереди dev на один коммит при одинаковом содержимом. Это ожидаемо. Чтобы не накапливать расхождение:

1. Создать следующую свободную mvsst-N от свежей origin/dev, задача — синхронизация истории релиза.
2. В её чистом worktree: `git merge origin/main`. Не применять squash; ожидается fast-forward либо
   merge истории. При параллельных изменениях dev разобраться в конфликтах обычным способом.
3. Если после выпуска dev не менялась, `git diff --exit-code origin/dev HEAD` должен показать нулевой diff.
   Если менялась — проверить, что merge main не откатывает её новые изменения.
4. Отправить ветку и PR mvsst-N → dev; CI, review, merge-коммит.
5. Проверить `git merge-base --is-ancestor origin/main origin/dev` после fetch. Следующий release PR
   не должен содержать повторное внесение уже выпущенных изменений.

Прямых push в dev, PR main → dev, reset dev на main и force push нет.
Автоматический тест `.github/scripts/sync-strategy.test.cjs` моделирует три выпуска,
включая одновременную разработку в dev: содержимое сохраняется, main возвращается в ancestry dev.

## Завершённые ветки

После merge ветка перестаёт быть рабочей. Перед удалением — fetch, проверить её полный SHA,
`git merge-base --is-ancestor <ref> origin/main` (или dev для ещё не выпущенной задачи), историю PR,
уникальные коммиты и все доступные worktrees. Закрытый PR сам по себе ничего не доказывает.
При squash или дополнительных merge-коммитах требуются отдельные доказательства эквивалентности.
Кандидатов представить владельцу с SHA; удалять только явно одобренные ветки после повторной проверки SHA.
Не удалять main/dev, активные mvsst-N и чужие worktrees. Ветки с уникальными коммитами сохранять
до отдельного решения. При необходимости архивного тега сначала согласовать его имя и SHA.

## Безопасный переход и исключения

Первое внедрение — организационный PR mvsst-1 → dev, созданной от исходной main.
До появления gate в целевой ветке доверенная проверка pull_request_target отсутствует; bootstrap-проверку
направления выполняет Quality из PR, а человек отдельно проверяет diff. Это одноразовый переход,
не постоянная лазейка. Порядок блокировки и первоначального включения main описан в GITHUB_PROTECTION.md.
Любые последующие изменения регламента — новая mvsst-N → dev после отдельного поручения владельца;
обязательные проверки и review остаются включёнными. Не добавлять label/bot/bypass-исключения.

Default branch рекомендуется dev, но переключает владелец после проверки внешних интеграций.
Существующий deploy/update.sh выполняет pull текущей checkout-ветки: на production должна быть
явно выбрана main. Скрипты и серверы в этой задаче не меняются.
