# Обязательные инструкции агентам — весь репозиторий

Эти правила действуют для Codex, Claude, Copilot и других исполнителей во всех каталогах.
Это единственный источник правил Git; технический контекст — `CLAUDE.md`, примеры — `docs/GIT_WORKFLOW.md`.

## До изменения файлов

1. Проверить каталог и репозиторий: `git rev-parse --show-toplevel`, `git remote -v`,
   `git branch --show-current`, `git status --short --branch`, `git worktree list --porcelain`.
2. Сохранить чужие незакоммиченные изменения. Не делать автоматический stash, reset или clean.
3. Выполнить `git fetch origin`. Прочитать доступные инструкции и проверить локальные/удалённые ветки,
   открытые PR и назначение существующих `mvsst-N`. Чужой worktree/ветку не занимать.

## Ветки и PR

- `main` — production, `dev` — постоянная интеграция/будущая тестовая среда. Разрабатывать в них запрещено.
- Каждая независимая задача/сеанс получает одну уникальную `mvsst-N` от актуальной `origin/dev`.
  N — положительное целое без ведущих нулей. Использовать следующий номер после максимального когда-либо
  выделенного (ветки и история PR); сначала опубликовать резервирование, при коллизии взять следующий.
- Одну активную ветку использует один исполнитель. Продолжение своей задачи допустимо только после проверки
  назначения; новая задача обычно получает новый номер. Не создавать пустые ветки впрок.
- Разработчик делает коммиты, тесты и push только своей ветки; PR — исключительно `mvsst-N → dev`
  внутри этого репозитория. Review и обязательные проверки предшествуют merge.
- `main` принимает только PR `dev → main` из этого репозитория после явного согласования владельцем
  конкретного SHA. Успешный CI или merge в dev не являются разрешением на production.
- ИИ не инициирует release PR, не сливает main и не запускает production-деплой без отдельного прямого
  поручения владельца на этот выпуск. Назначение dev — будущий автодеплой тестовой среды после CI;
  push рабочей ветки не развёртывает приложение. Деплой настраивается отдельным заданием.
- Merge-коммиты сохраняют историю. После релиза синхронизировать main через новую mvsst-N от dev и PR
  обратно в dev (порядок в GIT_WORKFLOW); прямой PR main → dev запрещён.

## Проверки и конфликты

- Перед PR: `npm ci`, `npm run db:generate`, `npm run build -w @mvs/shared`, `npm run typecheck`,
  `npx tsc --noEmit -p apps/api/prisma/tsconfig.json`, `npm run test -w @mvs/api`, `npm run build`,
  `node --test .github/scripts/pr-policy.test.cjs .github/scripts/sync-strategy.test.cjs`.
  MySQL-тесты — только в изолированных тестовых БД;
  CI поднимает одноразовый MySQL. Пропущенные локальные DB-тесты явно указать, CI не обходить.
- Отставшую опубликованную ветку обновлять `git merge origin/dev` в своём worktree после проверки status.
  Не выполнять автоматический rebase/force push опубликованной истории. При конфликте изучить обе стороны,
  сохранить изменения других исполнителей, повторить проверки; если решение неоднозначно — остановить merge.
- По завершении сообщить ссылку на PR, результаты/пропуски тестов, SHA и фактический статус интеграции.

## Запрещено

- Прямой commit/push в main или dev; force push, удаление или перезапись этих веток.
- Любой PR рабочей/старой/fork-ветки в main; обход CI, review или защиты.
- Переписывать общую историю, удалять чужие ветки/worktrees или удалённые ветки без отдельного решения владельца;
  использовать `git push --mirror`, автоматическую перезапись dev или массовую очистку.
- Менять этот регламент, CODEOWNERS, контрольные workflows, rulesets, branch protection или доступы без
  отдельного поручения. Служебные изменения тоже идут через mvsst-N → dev, без постоянных исключений.
- Создавать дополнительные постоянные интеграционные ветки.
- Копировать в Git секреты, временные инструкции/логи, личные пути, настройки и окружение.
