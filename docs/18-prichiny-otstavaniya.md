# Причины отставания от графика

Поле доступно под каждой позицией работ во всех строительных направлениях, включая новые направления и направления с импортированными отчётами. Красным оно выделяется только при отставании от графика; у работ по графику — спокойное поле с подписью «Работа идёт по графику — причина не требуется», а если отставание устранено, сохранённая причина показывается серым с пометкой «Отставание устранено». В матрице блоки с причиной и ФИО показывает переключатель **«Причины и ответственные»**: по умолчанию он выключен, красные блоки — только у отстающих работ (у устранённых — серые). Такой же переключатель есть в карточке объекта на вкладке «Работы»: положение общее для матрицы и карточки в пределах направления и сбрасывается при перезагрузке страницы. Щелчок по ячейке матрицы открывает карточку объекта сразу на этой работе — строка выделена и прокручена в середину экрана; если в ячейке несколько позиций, переход ведёт к самой проблемной. Если у работы есть отставание или записанная причина, поле причины показывается и при выключенном переключателе, чтобы его можно было сразу заполнить. Щелчок по названию объекта открывает карточку с начала списка. Отдельная вкладка **«Причины отставания»** собирает работы направления с поиском по объекту, работе, тексту и ФИО, фильтрами «Только мои», «С отставанием» и «Без причины».

## Назначение ответственных

Администратор открывает **Конструктор направлений → нужное направление → Причины отставания**:

- «Ответственные по умолчанию» — один или несколько активных участников направления.
- «Отдельное назначение» у вида работ заменяет общих ответственных для всех его позиций. Чтобы вернуть общее назначение, снимите этот флажок. Пустое отдельное назначение означает отсутствие ответственных, без наследования.
- Если общее назначение пусто, можно использовать ответственных позиции и объекта (роли «Ввод», «Куратор», «Ответственный»). Повторяющиеся сотрудники отображаются один раз.
- Можно разрешить куратору редактирование причин и потребовать заполнение при отставании перед закрытием/блокировкой отчётной точки.

ФИО отображаются рядом с полем полностью. Назначение не выдаёт права менять объёмы или финансы. Участник с ролью «Просмотр», отдельно назначенный ответственным, может заполнять только причины. Сотрудник должен быть активным и иметь доступ к направлению; для самостоятельного входа ему также нужна учётная запись с разрешённым входом.

## Заполнение и история

Причина сохраняется **отдельной кнопкой «Сохранить причину»**. Ввод факта по-прежнему сохраняется своей кнопкой. Длина причины — до 2000 символов.

Назначенные сотрудники редактируют открытую точку. Куратор с соответствующим разрешением может редактировать закрытую точку, администратор — в том числе заблокированную. Причины импортированного направления ведутся отдельно от факта: исходные объёмы и источник импорта не изменяются.

Записи хранятся по паре «позиция работ + отчётная точка». В следующую точку переносится последняя причина той же программы, с явной подписью исходной даты. Новая правка создаёт запись новой точки; старые срезы сохраняются. Очистка причины сохраняется явно и прекращает перенос старого текста. При одновременной правке сервер возвращает конфликт: черновик остаётся доступен, а кнопка «Загрузить актуальную причину» позволяет получить сохранённое значение.

Черновики сохраняются в хранилище вкладки браузера отдельно для сотрудника, направления, периода и работы. Переходы между разделами и перезагрузка этой вкладки их сохраняют. Закрытие вкладки завершает хранение черновика; сохранённые причины остаются в базе. После отзыва права ввода показывается сохранённая причина и отдельно — несохранённый черновик с возможностью отмены.

Изменения причин и назначений попадают в журнал. Архивирование работы сохраняет причины даже при отсутствии внесённого факта. Повторная загрузка/очистка демо-данных учитывает причины как ручные записи и защищает их обычным механизмом сохранности.

## Обновление

Миграция `20261101000000_delay_reasons` добавляет таблицу `delay_reason`; существующий факт не меняется. Примените миграции, обновите Prisma-клиент и сборку API/интерфейса штатным способом развёртывания. Контейнер API применяет миграции при старте. Назначения хранятся в настройках направления; все редакторы этих настроек сливают изменения под общей блокировкой строки.

## Проверки разработки

Интеграционные тесты требуют отдельную локальную MySQL-базу с именем, заканчивающимся на `_test`:

```powershell
$env:DELAY_TEST_DATABASE_URL='mysql://USER:PASSWORD@127.0.0.1:PORT/mvs_delay_test'
npm run test -w @mvs/api -- src/entry/delay-reasons.integration.spec.ts
```

Для браузерных проверок подготовьте отдельную базу с демо-данными и демо-администратором, запустите API и интерфейс, направленный на эту базу. Скрипт создаёт временных сотрудников и восстанавливает настройки после тестов:

```powershell
$env:DELAY_TEST_DATABASE_URL='mysql://USER:PASSWORD@127.0.0.1:PORT/mvs_delay_test'
$env:DELAY_TEST_BASE_URL='http://127.0.0.1:15173'
$env:DELAY_TEST_ADMIN_PASSWORD='PASSWORD'
npx playwright test --config apps/web/playwright.delay.config.ts
```

Проверяются четыре направления, ширины 375/768/1366/1920 px, светлая/тёмная темы, полный вывод ФИО, сохранение и восстановление черновиков, конфликт версий, отзыв доступа, конструктор, карточки объектов, ввод, матрица и оба режима графика. Скриншоты — в `test-results/delay-reasons/`.
